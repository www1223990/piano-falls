## 弱起小节（anacrusis）

开头两三个音之后画面"空一段"、后面整体变慢，是**弱起小节**没算对：

- MuseScore **3** 把弱起长度写成属性：`<Measure len="1/4"><irregular>1</irregular>`
- MuseScore **4** 才用子元素 `<len>1/4</len>`

解析器原来只认子元素，于是把弱起小节当成整小节，**后面所有音符整体晚 3 拍**（实测 1.64 秒）。
现在属性和子元素都读。修好后同一份谱子的前几个音：

```
修前: 0, 0.273, 2.182, 2.455 …   ← 1.9 秒的洞
修后: 0, 0.273, 0.545, 0.545 …   ← 接上了
```

## 弦乐窗格（指板）的显示逻辑

四条弦 = 四个**竖列**，音高**横向**从左到右由低到高，四条弦共用一条触发线：

| 元素 | 含义 |
| --- | --- |
| 四个大色块 + 大字母 G/D/A/E | 色盲也能靠字母和色块位置认弦；每条弦一个 Okabe-Ito 颜色 |
| 每弦的键 | 只显示该弦实际用到的音高（默认 6 个，谱子更高就补到最高音） |
| 同弦内由浅到深 | 把位越高颜色越深（明度梯度，不依赖色相） |
| 黑键 | 该弦音阶里的升降音，画得比白键暗（×0.42），**按下时只在自己色相上提亮，绝不发白** |
| 触发线 | 所有弦共用一条，音符落点在同一水平线，才看得出音高顺序 |
| 演奏中整段发光 | 该弦有声时整列亮起；空弦只有发光、没有按键 |
| 换弦弧线 | 从前一个音的**尾**连到后一个音的**头**（尾连头），后一个音落地后立刻消失 |

音高归属规则：`assignString` 取"空弦 ≤ 音高"的最高一条弦，所以每条弦覆盖 [空弦, 下一条空弦)。

### 分隔线：只在黑键下面

- **黑键那一排完全不画分隔线**（黑键之间不能有缝）
- 粗黑线从**黑键下沿**开始往下，穿过白键下段和四个大色块
- 分隔线横坐标对齐到交界处那个黑键的中心（`state.cutKeys`），不是两段区间的中点
- 交界那个黑键**整块保留不裁**（`state.cutMids`），其余键照常裁到本段区间，颜色不会串
- 每段最靠边的**白键**补到分隔线边上（黑键保持自然宽度）

相邻两条弦在键盘上的音域会互相压进去半个键宽，所以两段之间切一刀，每个键、每条下落音符、
每个色块都裁到自己的区间内（留出 `KEY_GAP`），分隔线盖住那条缝。

## 播放控制的一个坑：空格会触发两次

播放按钮拿到焦点后按空格，浏览器会**同时**触发我们自己的 `keydown` 处理**和**按钮自身的空格激活，
一次空格变成两次 toggle（`toggle(pause) → toggle(play)`），状态机翻转过头就会落到"从头开始"。

修法：`togglePlay()` 里 250ms 去抖（`lastToggleAt`），不管哪个事件先到都只认第一次。
实测一次空格 = 一次暂停/继续，位置保持（0:33.3 暂停 → 继续从 33.4 播）。

## 布局：琴键高度可拖、贴住控制栏、控制栏可收起

- **琴键高度**改成"占窗格高度的比例"（`keyFrac`，默认 0.28），不再是固定世界高度。
  鼠标移到**琴键上沿**会出现一条蓝色拖拽带，上下拖动即可改比例（12%–55%），存在
  `localStorage: piano-falls:keyfrac`。
- **琴键下沿贴住控制栏上沿**：底部留白不再写死，按控制栏真实 `getBoundingClientRect()` 计算
  （`syncBarInsets()`），窗口缩放/控制栏高度变化都会重算。
- **播放时控制栏收成一条小白条**（190×10，圆角），点一下才展开。
  **完全手动**：播放/暂停/停止都不会自动收起或展开，只有点把手 / 点小白条才变。
- 展开状态下，控制栏顶部中间有一个**小把手**（`#barGrip`，64×5），点一下也能收起。
- **空格只做一件事**：按下时先把焦点从按钮/滑块上摘掉（`blur()`），
  否则浏览器会把同一个空格当成"激活当前控件"，一次按键做两件事
  （表现为点过某个控件后要按两次空格控制栏才收回）。
## 踩过的坑（都是真金白银）

- **`<tempo>1.916667</tempo>` 对应 115 BPM**，即 `bpm = tempo × 60`（不是 120）。
- **三连音用 `<endTuplet/>` 显式结束，里面的休止符也参与缩放**。按 `actualNotes` 计数会在第 N 个音后提前关掉，导致小节时值超出（1680 vs 1440）——自检抓出来的。
- **MuseScore 4.7 起 `<Part>` 里的 `<Staff>` 没有 id 了**，谱表归属只能按出现顺序推。
- **`OrthographicCamera` 的 `top/bottom` 是相对相机中心的偏移**，不是世界坐标。一开始当成世界坐标填，可视区域跑到 y=13.96~43.48，键盘整个在画面外。
- **PowerShell 5.1 读无 BOM 的 .ps1 按 ANSI 解析**，中文注释会把后面的引号吃掉；`D:\音乐` 这种中文路径要写进脚本，得用 `[char]0x97F3` 拼。
- **`tonejs.github.io` 在这台机器上不可达**，采样要走 `cdn.jsdelivr.net/gh/Tonejs/audio@master/salamander/`；`D#1.mp3` 的 `#` 会被当锚点截断，实际文件名是 `Ds1.mp3`。

## "多出一路音频"的两个来源（已修）

1. **两个引擎同时出声**：分轨/原谱音频在播时，Tone.Transport 合成引擎如果还挂着旧排程，
   会在音频之外再响一路。它的特点是"暂停停不掉、只有按停止才消失"——因为暂停只停音频播放器。
   修法：进音频分支时先 `killSynth()`（stop + cancel + releaseAll），进合成分支时先 `player.stop()`，
   同一时刻只允许一个引擎出声。
2. **换谱后旧备轨把播放器劫走**：上一首还在后台渲染分轨，渲完调 `switchToStems()` 会把播放器换成
   **旧曲子**的音频（听起来就是"莫名其妙多出一段音频"）。修法：备轨加令牌 `stemsToken`，
   换谱就让旧结果作废。

## 变速播放

控制栏新增「速度」滑条（0.5×–1.5×，步进 0.05），值存在 `localStorage: piano-falls:speed`。

- 音频路径：每个 `AudioBufferSourceNode.playbackRate = rate`，`time()` 里乘上 `rate`
  （`startOffset + (now - startCtx) * rate`），所以画面、进度条、暂停/继续都按变速后的时间走。
- 合成路径：`transport.playbackRate = rate`。
- **注意**：这是改播放速率，音高会跟着变（0.5× 低一个八度）。要"变速不变调"得引入 granular
  时域伸缩（Tone.GrainPlayer 或自写 phase vocoder），目前没做。

## 网格

小节线 `#6fa8dc` / 拍线 `#3d6b96` / 八度竖线 `#5487bd`，线宽 0.07 / 0.03，
原来那几个色（`#233f5c`、`#17293c`）在 `#080d16` 背景上几乎看不见。

## 变速不变调（用浏览器自带能力，不造轮子）

`AudioBufferSourceNode` 只有 `playbackRate`（变速必变调），要不变调得自己写 phase vocoder
或引 soundtouch。这里改用 **`<audio>` 元素 + `HTMLMediaElement.preservesPitch`**：
浏览器（Chrome/Edge）内部就是做时域伸缩的，YouTube 那种变速不变调就是这个。

- `src/media-player.js`：统一播放器，1 轨（整轨）或 N 轨（分轨）都用它，
  接口和原来的 AudioPlayer/StemPlayer 一致（`load/play/pause/seek/stop/time/duration/
  setVolumeDb/setRate/setMute/dispose`），main.js 直接换。
- 多轨同步：所有 `<audio>` 同时 `play()`，另有看门狗每秒比对 `currentTime`，
  偏差 > 40ms 就拉回主轨。实测两轨 4 秒后 `currentTime` 完全一致（漂移 0ms）。
- 变速实测：0.3× 时真实 1.5 秒曲子走 0.45 秒（正好 0.3），`preservesPitch = true`。
- 音量/静音：`el.volume`（静音的轨置 0）。

## 倚音（grace note）不能算拍子

带斜杠的小音符（acciaccatura / grace8…64）在 mscx 里**也带 `<durationType>`**，
但它零时值。早先 `eventTicks()` 按 durationType 算，于是每个倚音吃掉一整个八分音符，
后面的所有音符被推后——表现为"过一小段才追回来"，而且小节起始处会空出一块。

现在：

- `isGraceChord()` 认 `<acciaccatura/>`、`<grace8|16|32|64/>`、`<graceNoteType>`
- 倚音 `dur = 0`，**不推进 cursor**
- 渲染时把它放到主音前 0.07s、时长 0.06s（看起来就是"飞快的一下"）

实测：两个倚音在 t=53.089（dur 0.06），主音在 53.159，时间轴连续无洞。

## 多小节休止（multiMeasureRest）不占时间

`<Measure len="8/4"><multiMeasureRest>2</multiMeasureRest>` 是 MuseScore 的**压缩显示**：
它把 N 个小节画成一个小节。按 `len` 算会多出 N 个小节的时长——实测《雑踏、僕らの街》
两处 8/4 各多算 2.8 秒，**画面到最后累计晚 5.6 秒**。

以渲染音频为准（用 MuseScore 导出的 MIDI 逐音对照）：
这类小节**本身不占时间**，真正的时长由紧随其后的占位小节承担，所以 `measureLength()` 返回 0。

修完对照结果：全程中位数偏差 0，最后一个音 180.9s 与音频完全一致（修前 -5.6s）。

## 速度表仲裁：用音频真实长度当裁判

MuseScore 导出的 MIDI 速度表**偶尔带多余的结尾变速**（实测《Cancan》末尾多一个 78 BPM 标记，
音频里根本没有），按它把 tick 换算成秒会把结尾拉长一倍——画面越放越晚，累计到 3 秒以上。

现在 `scoreFromMscx` 同时构建两张速度表：

1. **MIDI 的**（`timing.tempos`）——通常最准
2. **谱面自己的**（`parsed.tempos`）——作者标的 tempo

然后用**渲染音频的真实长度**（`decodeAudioLength()` 离线解码得到，mp3 的 duration 属性是估算值）
当裁判：两张表各算"最后一个音的结束时间"，谁更接近音频长度就用谁（`score.tempoSource` 可查）。
拿不到音频长度时退回"用 MIDI 音符时间算拟合误差中位数"。

实测《Cancan》：谱面表算出 132.31s（展开 172 小节）、音频 136.15s（末尾 4.6s 是编码静音）✓ → 选谱面表；MIDI 表会算成 142.31s ✗。

## 尾部裁剪 + 播放时间校正（反复/延长记号的坑）

谱面有反复（`<startRepeat>/<endRepeat>`）、结尾反复（`<Volta>`）、小节重复（`<measureRepeatCount>`）
和延长记号时，"书面位置"和"实际演奏时间"不是一回事：

- 速度表（tick→秒）按书面位置算，会和音频差好几秒
- 实测《Cancan》：谱面 130 小节，展开后实际演奏 172 小节；最后一个音在 131.54s
  （修复早期"每个反复段弹两遍"那版展开会算成 178 小节 / 136.92s，画面比声音晚 3.6 秒以上）

现在的处理（按顺序生效）：

1. **反复展开**按 volta 语义算出真正的演奏顺序（见下面专门一节），这一步做对之后时间轴才成立
2. `tempoSource` 仲裁（见上一节）：选和音频长度最接近的速度表
3. **尾部裁剪**：MIDI 的最后一个音就是音频里最后一个真实发声点，晚于它 0.5 秒以上的音符直接丢掉
   （`score.midiLastNote` 可查）。展开正确后这一步**不再丢任何音**，只剩兜底作用：
   《Cancan》最后一声 131.538s = MIDI = 音频里那一声 ✓
4. 偏差 > 0.5s 的音符用 MIDI 的真实时间替换（`makeSnapper`），正常音符不动

# 反复段展开（已实现）+ 三个连带 bug

这一节是上一轮留下的坑，本轮已经修完了。留着是因为**症状和判断过程比代码值钱**——
上一轮就是没先打印结构表、直接写展开，把音符数炸到 14654 才回滚的。

## 症状与根因

用户的描述是："画面有延迟，中间可能卡一下，卡了之后会恢复正常，但接着又会慢慢累积延迟"，重点在反复段。

根因不在渲染，在**播放顺序**：`src/mscx.js` 里那版展开是"每个 `<endRepeat>` 段一律弹两遍"，
完全不看 `Volta`（1./2. 结尾）。拿《Cancan》一算：

| | 谱面 | 两遍 | 正确（volta） | MIDI 实测 |
|---|---|---|---|---|
| 小节数 | 130 | 178 | **172** | 171.5 个 0.769s |
| 最后一声 | — | 136.92s | **132.31s**（最后一小节起点 131.54） | **131.54s** |

多出来的 6 小节 = 4.6 秒，全压在第 17 小节之后 → **m17 之后画面整体偏晚**，越往后越晚。
`makeSnapper`（偏差 0.5~5s 用 MIDI 时间替换）会时不时把挨得近的音"拽回来"，
于是听感/观感就是"卡一下恢复正常 → 再慢慢累积延迟"。**症状和根因的对应关系到这里才对上。**

## MuseScore 里的写法（都实测确认过）

```xml
<Measure>
  <startRepeat/> / <endRepeat/>            <!-- 反复记号，Measure 直接子元素 -->
  <repeatCount>3</repeatCount>             <!-- 省略 = 弹 2 遍 -->
  <measureRepeatCount>1</measureRepeatCount><!-- "%" 小节重复：本小节内容是空的，借用上一小节 -->
  <voice>
    <Spanner type="Volta"><Volta><endings>1</endings></Volta>
      <next><location><measures>2</measures></location></next></Spanner>  <!-- 1. 结尾，占 2 小节 -->
    <Spanner type="Ottava"><Ottava><subtype>8va</subtype><play>0</play></Ottava>
      <next><location><measures>7</measures></location></next></Spanner>  <!-- 八度线；play=0 = 只显示不移调 -->
    <Chord>…<TremoloTwoChord><subtype>c16</subtype></TremoloTwoChord></Chord>
```

注意几个反直觉的点：

- 没有 `<endings>` 的 `Volta` 只是排版续接（MuseScore 会多写一份），必须忽略，否则 span 全是 0
- `Volta` 和 `Ottava` 都在 `<voice>` 里面，不是 `<Measure>` 的直接子元素
- `<play>0</play>` 的八度线（"loco" 那种）**不能**移调
- **`Volta` 和 `Ottava` 的 `<measures>` 是两种语义**（这里踩过一个"少移一个八度"的坑）：
  - `Volta`：这一段占 N 个小节（从它所在小节算）
  - `Ottava`：**从线条起点往后 N 个小节的 tick**。起点常在小节中间，
    所以 `measures=7` 起在小节第 1.5 拍时，会盖到第 8 小节的前 1.5 拍。
    用"整小节"算就少盖最后一小节（Cancan 的 m8 画低一个八度，实测 MIDI 那两音是 +12 的）
- 两音颤音 `TremoloTwoChord`：一个 2/4 小节里写着两个半音符，实际是两组和弦在整小节内
  **按 `<subtype>` 交替**（`c16` = 十六分，Cancan 结尾每小节 8 次交替，和 MIDI 逐音对得上）。
  两个和弦是**同时**占一小节的，按顺序排会溢出（`1920≠960`，多出来的音压到下一小节）

## 实现（`src/mscx.js`）

- `buildPlayOrder()` 产出 `{ index, src }[]`：`index` = 谱面小节下标，`src` = 借哪一小节的内容（`%` 用）
- `voltaOf()` 读 `endings` + `span`，按"这一段覆盖哪几个小节"预proces成 map
- `pass` 语义：`<startRepeat>` 处 `curPass = 1`；`<endRepeat>` 处 `curPass++`，
  小于 `repeatCount` 就跳回段首，等于就结束本段并**停在最后一遍**（段后的"2."结尾才能被弹到）
- 遇到不该弹的结尾（`endings` 不含 `curPass`）整段跳过；若被跳过的段里含 `<endRepeat>`，
  按"这一遍已经弹完"结算（否则 `repeatCount` 在结尾小节上的谱子会死循环）
- **硬断言**：`order.length > 谱面小节数 × 1.3 + 4` → 退回顺序播放 + 警告。宁可少画，不能炸
- `%` 小节：`src` 往前找到真正有内容的小节（可能连着好几个 `%`），tick 用本小节的
- `TremoloTwoChord`：先记住第一组和弦（`pendingTrem`），第二组到了再一起铺 A/B/A/B…
  （`emitTremolo`，间隔查 `<subtype>`：c8/c16/c32/c64）；游标直接推到小节末，两组和弦不会被当成先后两个半音符
- 八度线：**预扫**小节登记区间 `{ start, end: start + span×小节长, shift }`（`ottavaSpansOf`），
  发音符时按音符 tick 查（`shiftAtTick`）。必须预扫：线条可能写在**后面的声部**里，
  等走到它时前面声部的音已经发出去了（Cancan m1 就是这么漏掉的，前两个音低了八度）

## 收尾：结尾那 4.6 秒空白

谱面在 131.54s 结束，但 mp3 文件长度是 136.15s（编码静音）。原来 `totalDuration()` 取
`max(音频, 谱面)`，于是结尾要空转 4.6 秒（"结尾还是有空白"就是这个）。

现在：`totalDuration() = 谱面结束 + 0.6s 余音`（音频明显更长时才这样压），
主循环里 `player.time() > totalDuration()` 就 `stop()`，进度条和画面都不会空转。

## 连带 bug：两音颤音让"分轨备好"失败

修反复的时候顺手抓到一个更隐蔽的：分轨（按谱表静音）一直失败，状态栏写
`分轨准备失败 … render failed: MIDI export failed`。

原因不在渲染服务器，在 `src/mute.js`：静音是把 `<Chord>` 换成等长休止符，
而两音颤音的"两个半音符"是**同时**演奏、只占一小节——各换一个休止符之后，
这个小节就变成 4 拍（2/4 里放不下），MuseScore 直接拒绝导出（exit≠0）。

修法：带 `<TremoloTwoChord>` 的和弦换成一个休止符，紧跟的那个"另一半"整个删掉。
现在《Cancan》分轨正常（状态栏：`音源 MuseScore 分轨（可即时静音）`），
定位脚本留在 `tools/bisect-mute.mjs`（二分找哪一小节炸，一次跑完）。

## 修：多轨（分轨）播放时"每秒卡一下 / 声音像被重置"

**症状**：分轨播放时每隔约 1 秒有一次细微的顿挫，像音频被"重置"了一下；另一只手的声音一直比画面晚一点点。

**根因有两层，第二层才是真凶**：

1. 换分轨那一刻，两条 `<audio>` 的起播时刻不同步（实测差 60~78 ms：`20.80 / 20.74`）。
   发生在"播放中切换"这条路上；命中缓存、加载时就绪的情况实测偏差恒为 0。
2. 旧代码有个"每秒看门狗"：发现两轨差 >40 ms 就 `el.currentTime = master`。
   但实测 **对正在播放的 `<audio>` 写 `currentTime` 会让它停顿 56~68 ms**（≈ 偏差量），
   于是"刚修好"的下一秒偏差又回来，看门狗再修一次 —— **每秒一次 seek，每次丢 56~68 ms 音频**。

实测证据（往第 2 条轨注入 70 ms 偏差）：

```
1025ms  写 5.947（当时 5.891）
2025ms  写 6.946（6.890）
3025ms  写 7.943（7.888）
4025ms  写 8.942（8.874）
偏差序列：0.056 … 0.004(刚修好) … 0.056 … 一直循环
```

**修法（`src/media-player.js` + `src/main.js`）**：

1. 换分轨时 `await next.ready()`：等到 `canplaythrough`（能立刻出声），不是只等元数据
2. 偏移校准（要离线解码 2 MB）挪到**起播之前**，别和起播抢 CPU
3. 删掉"每秒 seek"的看门狗。改成：
   - 起播后 400 ms / 2500 ms 各量一次；只有真的大于 20 ms 才建一层 WebAudio
     （`<audio>` → `DelayNode` → `destination`），用 delay 把**早的那条**延后，改 `delayTime` 不会让元素停顿
   - 主轨取"最慢的那条"（它的 delay 恒为 0，所以画面不会被平移）；`time()` 再减掉主轨 delay 兜底
   - 之后每 8 秒低频复查一次，只有大于 40 ms 才动
4. 静音仍是 `el.volume`（经过 `MediaElementSource` 后依然生效，实测 RMS 变 0）

**为什么只在跑偏时才建这层图**：正常播放完全不碰音频通路，零风险；
跑偏是小概率事件（换分轨 + 调度抖动），那时再建一次。

**验证（浏览器实测）**：

| 场景 | 结果 |
|---|---|
| 正常播放 35 秒（分轨） | spread 最大 0.2 ms，播放期间 0 次 `currentTime` 写入，不建图 |
| 注入 70 ms 偏差 | 建图、给早的轨加 0.07s delay、spread → 0、**0 次 seek**、两轨时钟照常走 |
| 播放中换分轨 | spread 0，时间连续（25.92 → 25.94，无跳变） |
| 拖进度条 | 4 次写入（都是拖动的正常 seek），之后 spread 0.1 ms |

回归测试：`test/test-media-player.mjs`（假 `<audio>` / `AudioContext`），已并入 `npm test`。
其中两条专门锁死"**不许用写 currentTime 的方式修同步**"。

### 补一刀：那声"激光"

用户反馈播放时会冒出"莫名其妙的像激光的声音"。查下来是**对齐用的 delay 拉得太大**：
起播抖动时两轨可能差 300~500 ms，`delayTime.setTargetAtTime(0.34, …, 0.03)` 相当于
让那条轨在 30 ms 内滑音半个八度 —— 听感就是"滋～"一声。实测日志里能抓到
`ramp=0.3413` / `ramp=0.5`（0.5 是钳位上限）。

现在的规矩：

- **delay 只修 ≤120 ms 的偏差**（`ALIGN_MAX`），时间常数放到 0.15 s（变化更平缓）
- 偏差 >120 ms 时不再加 delay，改**一次性硬对齐**：暂停全部轨 → 统一 `currentTime`（取最大位置）→ 继续播。
  会有几十毫秒的断续，但不会滑音；30 秒内最多 4 次，避免变成"每次卡一下"
- 偏差 >5 s 视为异常状态：不硬来，HUD 显示"⚠ 分轨不同步 XXXms（重播可恢复）"

验证：人为把一条轨推后 350 ms，`_alignTracks()` 只产生 2 次 `currentTime` 写入（两轨各一次）、
**0 次 delay ramp**，之后 spread = 0；正常播放 8 秒内 0 次写入、0 次 ramp。
